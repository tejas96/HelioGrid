# @heliogrid/i18n — ONE Lingui catalog (EN/HI/MR) for Next.js AND bare RN

## What lives here / what must never live here
- .po catalogs (src/locales/*/messages.po — the translation source of truth), their
  COMPILED messages.ts (generated by `lingui compile`, committed, biome-excluded), the
  LANGUAGE_META table, the catalog loaders, the runtime/translator factories and the ONE
  React provider both platforms use.
- The @lingui and @formatjs DEPENDENCIES. Neither app declares them — one package owns the
  message library, so swapping it touches `src/react/` and nothing in either app.
- Shared cross-platform copy modules in `src/copy/` — pure data, extractor-swept via
  leading `/*i18n*/` message descriptors, with NO React and no `@lingui/react` import
  (`src/copy/api-error.ts`'s header states the dual-instance ESM/CJS reason and is the
  canonical explanation). Where a closed set exists, the module is a `Record` over the
  contracts enum. Screen-specific copy stays in its screen.
- NEVER: app copy hard-coded elsewhere, per-app catalogs, the language LIST (that is
  `packages/contracts/src/locale.ts`), agent/WhatsApp templates
  (tenant DATA — `docs/prd/foundations/F3-localization.md` · .claude/rules/i18n.md), raw Intl currency (formatMoney when
  domain's money slice lands).

## Three entry points
- `.` — REACT-FREE. `createI18nRuntime(locale)` for a mount, `createTranslator(locale)` for
  isolated server/background/export work, `LANGUAGE_META`, `loadCatalog`, the copy modules.
- `./react` — `HelioI18nProvider`, `useI18n`, `useTranslate`, and the re-exported `<Trans>`.
- `./rn` — the Hermes Intl polyfills. Separate because importing it INSTALLS GLOBALS; a web
  bundle must never reach it, which a shared root export could not have prevented.

## THE CONVENTION (until the swc-plugin note below is resolved)
Both platforms use runtime `<Trans id="<English source text>" />` from `@heliogrid/i18n/react` —
the id IS the English string, so ids double as msgids and the extractor keeps ONE entry
per message. Do NOT mix macro `<Trans>` and explicit-id usage for the same string: the
extractor forks them into duplicate .po entries (hit 2026-07-26, cost translations).

That convention is also why the first paint is correct with no catalog fetched at all — a
missing message renders its id, which is the English text.

## Local conventions
- **The language SET is not written here.** `UI_LANGUAGES` in
  `packages/contracts/src/locale.ts` is the one authoring; `lingui.config.js` reads it too.
  `LANGUAGE_META` and both catalog loaders are `satisfies Record<UiLanguage, …>`, so a new
  contract language fails typecheck until it is registered. The THIRD registration — Hermes
  plural-rule data — is a bare side-effect import no type can see, so it is held by
  `scripts/check-adherence.sh` check 9.
- **One instance per mount and per request. Never a module-scope one.** Next evaluates a
  module once per server process and shares it across every request; a module-level
  `setupI18n()` is one mutable active locale for every concurrent visitor. It was exactly
  that until 2026-08-25.
- **`t(id, values)` for hooks and handlers; `<Trans>` in markup; `createTranslator(locale)`
  off the React tree.** Store message IDs plus data — never a translated business record,
  which is wrong for every other reader of it.
- **UI language is not the tenant MARKET.** Language is per user; currency grouping, tax
  scheme and paperwork come from the market pack. A Marathi-reading user in an Indian tenant
  still sees INR in lakh/crore. Never derive one from the other.

## Landmines
- **The catalog loader is platform-FORKED, and it has to be.** `catalog-loader.ts` uses
  `import()` so webpack splits one chunk per language; `catalog-loader.native.ts` (Metro
  substitutes it) imports all three statically. React Native ships ONE bundle: a release
  build inlines the `import()`, but against the DEV SERVER the same call goes through
  `__loadBundleAsync` and throws `LoadBundleFromServerError: Could not load bundle` — hit on
  the iOS simulator 2026-08-25, where switching to Hindi failed and the UI stayed English.
- **The source catalog is imported STATICALLY** (`languages.ts`). Without it,
  `i18n.activate()` warns "Messages for locale … not loaded." on every boot, and in a
  PRODUCTION build — where Lingui's dev message compiler is absent — every fallback message
  `console.warn`s "Uncompiled message detected". Both proven, then fixed, 2026-08-25.
- **`lingui.config.js` requires BUILT contracts.** It is CommonJS and runs outside any TS
  pipeline. It throws loudly rather than falling back to a local list: a silent fallback
  would extract against the wrong language set with every gate green.
- **`installFormsErrorMap` mutates zod's PROCESS-GLOBAL error map**, so it cannot be
  per-request. It is installed by each app root, bound to that mount's translator — correct
  on a client, where one mount has one language. Server-side translation uses
  `createTranslator` and never touches it. A server-rendered form needing translated zod
  defaults is a new decision.
- **`@lingui/swc-plugin` (5.11.0 AND 6.6.0) fails against Next 15.5.21's swc_core**
  ("failed to invoke plugin") — that's why web can't use macros yet. Revisit on Next or
  plugin bumps; migrating BOTH platforms to macros is then one mechanical sweep (ids
  already equal source text).
- Compiled messages.ts are generated — never hand-edit; excluded from Biome.
- Hermes needs the Intl polyfills BEFORE any ICU call — hence `@heliogrid/i18n/rn`, imported
  first from `apps/mobile/src/i18n.ts`.

## Definition of done here
extract leaves the tree clean (CI guard) · all locales 0 missing or the gap is
deliberate (English fallback) · every language RENDERED on web and both simulators —
switching, not just loading · the web build shows inactive catalogs outside the initial
chunk, and the RN bundle shows one copy of each runtime.

## Folder shape

`src/` with everything public re-exported from `src/index.ts`. Consumers import the index,
never a deep path. Never invent a folder: this tree is a closed set.
