## Round 17 closed all 46 — and that round is deliberately not verified

Rounds 17A/17B/17C and 17DA/17DB/17DC corrected every one of the 46 partials above, plus the
eleven law conflicts and the three instruments. **The table below still shows the 2026-08-17
verdicts**, because those are the last verdicts anyone actually measured — regenerating them from
a session's own report would be the exact error this register exists to prevent.

**There will not be a fourth verification pass, and that is a decision rather than an oversight.**
The 2026-08-16 audit found 34 blockers. The 2026-08-17 pass found **zero** that stopped a screen
being drawn, and a tail of documentation drift. A fourth pass would cost what the third did
(~7.8M tokens, 42 agents) to find a smaller tail again. The yield curve has turned over.

What replaces it is better than a pass: round 17 made three instruments real, and they run
**inside the project on every load** rather than once when someone asks —
`guidelines/touch-targets.card.html` (inventory from `_ds_manifest.json`, results persisted to a
baseline with a drift pane), `guidelines/color-contrast.card.html` (rasterises live tokens instead
of quoting transcribed strings), and the card-health check. The next drift is found by the system,
not by a workflow.

**The real test is screen one.** A design system is verified by being used, and 56 drawable
screens will find a genuine defect faster and cheaper than any further reading of the same files.

## How the 57 were found

On **2026-08-16**, eleven agents read all **99 V1 briefs** in five slices and checked each
brief's needs against the **live** Claude Design project `c8aa4326-21bf-453a-8d11-749cc81dee12`
— opening the `.jsx`, the `.d.ts` and `readme.md` of every component named, never reasoning
from a component's name.

| slice | first pass | after refutation | components checked |
|---|---|---|---|
| Block 1 — shell, entry and tenant (23 screens) | 13 | 17 | 69 |
| Blocks 2–5 — billing, CRM, projects, payments (21 screens) | 17 | 23 | 32 |
| Block 6 — sales execution, calling core, owner home (12 screens) | 12 | 18 | 37 |
| Block 7 — the 3D design studio (18 screens) | 22 | 30 | 55 |
| Block 8 — proposals and the customer link (25 screens) | 14 | 20 | 52 |

**186 raw reports → 57 distinct gaps.** Nearly every finding arrived at least
twice, because each slice ran a first pass and then an adversarial pass against itself.

A gap reported by all five slices is a **token- or law-layer** problem. A gap reported by one
slice is a **surface**. That distinction is why the closed ones are closed first — they are
the ones all 99 screens inherit.

## The two ways a design system fails

Every gap is one of these, and the second is the dangerous one:

- **absent** (23 gaps) — the component does not exist.
- **present-but-wrong** (34 gaps) — the component exists, carries the right name, and its API
  contradicts what the screen needs. Nothing looks missing. This is the failure mode that has
  produced every false all-clear on this project.

Severity splits **34 blockers / 23 defects**. A blocker means a screen cannot be drawn
honestly; a defect means it can be drawn but something is wrong.

## How to read the status column

| mark | meaning |
|---|---|
| `✓ closed` | re-read in the live files after the round ran, **and** survived a skeptic sent to refute it |
| `◐ partial` | landed in part; the verified remainder is quoted in the gap's own entry |
| `▸ sent` | a round addressed it; **not yet verified** — sent is not landed |
| `○ open` | never sent |

**The status column is not my recollection.** It is generated from
[`_audit/2026-08-16-closure-verification.json`](_audit/2026-08-16-closure-verification.json)
— a second pass that re-opened the live `.jsx`, `.d.ts`, `.prompt.md`, spec cards and templates
after rounds 11 and 12 ran, then sent an adversarial reader at every `CLOSED` verdict with
instructions to default to refuted when unsure.

**It overturned 9 of the 12 I had recorded as closed.** Three were refuted outright (gaps 3, 5, 9);
the rest came back partial on first read. The recurring cause is the same one this project keeps
hitting: the component lands, and its **documentation, spec card or template** is left teaching
the old behaviour — so the next person to copy the canonical snippet reintroduces the defect.

A gap is not closed because a prompt asked for it, and not closed because the component appeared.

#### Verified closed

> (a) OPEN VOCABULARY — yes. Provenance.d.ts: `export type ProvenanceTierSpec = ProvenanceTierName | "unmarked" | string | { label: string; tone?: ProvenanceTierName; color?: string };` with the header comment "The four canonical tiers. **Not a closed set** — any string is a valid tier". The runtime honours it rather than falling back to a default: `return PROVENANCE_TIERS[tier] || { label: toLabel(tier), color: "var(--text-tertiary)" };`, and `toLabel` deliberately does not rewrite caller prose — `const KEY_LIKE = /^[a-z][a-z0-9]*(?:[-_][a-z0-9]+)*$/;` … `return KEY_LIKE.test(raw) ? raw.replace(/[-_]/g, " ").replace(/^\w/, (c) => c.toUpperCase()) : raw;` ("An open vocabulary that rewrites the caller's word isn't open."). The triplicated closed union is gone: DataTable.d.ts now has `import { ProvenanceProps, ProvenanceTierSpec } from "./Provenance";`, UsageMeter.d.ts `import { ProvenanceTierSpec, ProvenanceStanding } from "../data/Provenance";`, Charts.d.ts `import { ProvenanceProps, ProvenanceTierSpec, ProvenanceStanding } from "../data/Provenance";` — none redeclares `ProvenanceTierName`. The per-file hard-coded TIERS tables are gone too: DataTable.jsx, Charts.jsx and UsageMeter.jsx all import from `Provenance.jsx` and the single `PROVENANCE_TIERS` object lives only there. M12-34 is satisfied concretely — UsageMeter.d.ts: "M12-34 reserves \"measured\" … forbids it on this screen, so pass this screen's own word — `\"Actual usage\"`", and usage-meter.card.html passes `provenance="Actual usage"`. >
> (b) SOURCE SLOT — yes, a separate prop, not folded into the tier. Provenance.d.ts: `/** What data it came from — `"Real · PVGIS (SARAH3)"`, `"Built-in estimate ±10%"` (`M05-54`). */ source?: string;`, rendered as its own part: `if (source) parts.push(<span key="source">{source}</span>);`. ### The standing instruction every round must carry

The closure verification found one cause behind nearly every partial landing, and it was never
the component: **the component landed and its documentation did not.** `AppRail.prompt.md` still
taught `badge: true` after `CountBadge` shipped. The rail's own spec card still drew a bare dot.
Two of three templates still showed the old form. A designer copying the canonical snippet would
have reintroduced the defect the round had just removed.

So every round from 13 on ends with this, and it is not optional:

> For each item, also update **every** surface that teaches the old behaviour — the
> `.prompt.md`, the `@dsCard` spec card, the templates under `templates/`, `readme.md` and any
> sibling component's docs that show the pattern. Then list which files you changed for each
> item. A component whose own example still shows the old form has not landed.

Adding this is expected to matter more than round size. Round 12 carried seven items and six
landed partially; every one of those six failed on documentation, not on the component.
