# HelioGrid Toolchain Recommendation — Monorepo, Lint/Boundaries, i18n, Agent Rules (July 2026)

## Single recommendation

**pnpm workspaces + Turborepo + TypeScript project references** for the repo; **Biome v2.5** as the one lint/format binary, backed by **dependency-cruiser** (layer/import rules) + **sherif** (dependency-version drift) + **Turborepo Boundaries** (package encapsulation); **Lingui v5** for the shared EN/Hindi/Marathi catalog across Next.js and Expo; **hierarchical `CLAUDE.md` + `AGENTS.md`** (lean root, per-package files, ADRs in `/docs/adr`). This stack is the most *legible and deterministic for AI agents* because every layer is plain, inspectable config (standard `package.json` + `turbo.json` + `biome.json`), not a generated project graph.

## Why this over the alternatives

**Monorepo — pnpm + Turborepo, reject Nx and moon.** Nx is genuinely faster (~7x on 50+ package repos) and has richer generators, but it introduces `project.json`, inferred targets, executors, and a plugin-inferred task graph — an abstraction layer an agent must reverse-engineer, and a frequent source of non-determinism ("why did this target run?"). For ~6 apps + ~10 packages you are far below the scale where Nx's speed matters. Turborepo keeps truth in native files: an agent reads `package.json` scripts + `turbo.json` `tasks` and knows exactly what runs. moon (Rust, declarative YAML, `moonbase` remote cache) is legible and polyglot-friendly, but at ~50K weekly downloads its ecosystem and training-data footprint are thin — agents produce more reliable code against Turborepo's dominant corpus. Turborepo also now ships **Boundaries** (2.4+): flags imports outside a package dir and undeclared-dependency imports, with custom tags for who-may-depend-on-whom — package-level enforcement without Nx. **Pricing:** Turborepo Remote Cache is free on Vercel and self-hostable (open protocol); Nx Cloud is credit-metered CI (free tier then paid per-credit); moonbase has its own paid cache tier. Turborepo is the cheapest path to India-region CI on Fly.io.

**TypeScript project references, not a single bundler-mode graph.** 2026 consensus: pnpm handles resolution, project references give incremental `tsc --build` and hard type boundaries between `domain`, `contracts`, `db`, `ui`. Ship source (not pre-built dist) to web/api since Next.js/Metro bundle downstream; keep references purely for typecheck ordering and enforced boundaries. This gives agents fast, deterministic `tsc -b` feedback per package.

**Lint/format — Biome v2.5, reject ESLint v9 + Prettier as the primary.** Biome is a single Rust binary, one `biome.json`, 20–100x faster (sub-500ms vs 15–30s on ~1000 files), with import sorting built in. For an agent, one config and one command (`biome check`) is dramatically more deterministic than ESLint flat-config + `FlatCompat` shims + Prettier coordination. Biome v2.5 (June 2026) hit 500 stable rules, cross-file linting, a stable GritQL plugin API, watch mode, and `noRestrictedImports`/`noRestrictedDependencies`. **Gap:** Biome still lacks a true Nx-style tag-based module-boundary rule, so don't rely on it alone for the layered import rules you need.

**Import boundaries — dependency-cruiser + sherif + Turborepo Boundaries; reject eslint-plugin-boundaries and Nx enforce-module-boundaries.** The last two require an ESLint runtime — adopting them pulls ESLint back in and defeats the Biome simplification. dependency-cruiser is standalone, config-as-code (`.dependency-cruiser.js`), and does exactly your layered rules ("domain may not import db", no cycles, no orphans) with a rule graph an agent can read and edit. It runs in CI as one command. Add **sherif** (Rust, zero-config) to catch the classic monorepo bug — a dependency bumped in one package but not others. Turborepo Boundaries covers physical package encapsulation. Together these three cover version-drift + package encapsulation + semantic layer rules without ESLint. Note the naming trap: **sherif** (QuiiBz) = dependency-version linter; **Sheriff** (@softarc) = ESLint-based boundary tool — you want the former, not the latter.

**i18n — Lingui v5, reject Paraglide, i18next, FormatJS.** Hard requirement: one catalog shared by **Next.js App Router + Expo**, Devanagari EN/Hi/Mr, runtime per-user switch, ICU plurals. **Paraglide (inlang) is out despite the best type-safety** — it has no first-class React Native/Expo support, a dealbreaker for your real mobile app. Lingui v5 is compile-based (small bundles, ICU MessageFormat native), officially supports **RN ≥0.76 / Expo ≥52 (Hermes) via `@lingui/metro-transformer`** *and* Next.js App Router + React Server Components, with a lightweight runtime for locale switching — uniquely satisfying "one catalog, both platforms." i18next runs everywhere but is runtime-heavy and needs manual declaration-merging for key type-safety (boilerplate agents get wrong). FormatJS/react-intl is heavier and weaker on RN DX. Caveat: Lingui's macro model uses natural-language message IDs, so key type-safety is via extraction + `messages.ts`, not typed functions like Paraglide — acceptable given it's the only compile-time option covering RN. **Pricing:** Lingui, Biome, sherif, dependency-cruiser all OSS/free.

**Agent rules — hierarchical, lean.** 2026 best practice: root `CLAUDE.md`/`AGENTS.md` under ~200 lines, commands-first (exact test/build/lint invocations), plus a focused per-package `CLAUDE.md` (Claude Code merges up the tree, so `packages/domain` loads its own + root). Keep architecture essays and full ADRs *out* of `CLAUDE.md`; store ADRs in `/docs/adr/NNN-*.md` and reference them. Symlink or dual-emit `AGENTS.md` for cross-tool compatibility. Omit anything duplicating the linter or `package.json` scripts.
