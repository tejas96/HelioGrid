# SCR-M01-01 · Sign In

Front door: phone + OTP entry with Google Login alternative.

**Module:** M01 · **Personas:** All users; all studio personas · **Context of use:** the one screen every person passes through, on web and mobile equally. Employees arrive "Phone, almost always" (M01 §2); the owner is often on a laptop. Runs before roles exist — nothing here is permission-gated. The rebuild acceptance list carried at M01 §6 (M01-Q3/register Q20) binds this screen: signed-out routing decided once for both platforms, success-dwell timing, visible resend feedback on every platform.

## Entry & exit

Reached from: any signed-out launch of the app or web product (signed-out routing decided once for both platforms — M01 §6 Q20 ruling). Leads to: on success, tenant, user and role context is established (MS12-17) and the person lands on their role-decided home (M01 §M01.2, M01-17 — mechanics are `docs/prd/modules/M13-dashboards-and-reporting.md`'s). A first Google sign-in runs the linking flow onto the phone-identity account (M01-02). The path for a phone number with no account (hand-off to Company Signup, SCR-M01-02) is not pinned by PRD — designer decides, note the decision.

## Requirements (verbatim)

### From `docs/prd/modules/M01-onboarding-and-tenant-config.md`

- **M01-02** (P0) — **Google Login is supported alongside Mobile OTP — as a convenience sign-in bound to the SAME phone-identity account (owner ruling 2026-08-04, Q18).** Both sign-in methods exist on web and mobile; the account identity remains the phone number (M01-18), and a Google identity is **linked** to that phone-identified account at the **first Google sign-in** via the linking flow — never creating a duplicate account, and never standing in for the verified phone. A brand-new signup completes phone verification as part of becoming an account; Google is the convenience door onto it. Architecture stays future-friendly for further methods. _(non-UI half, build-side: Google identity links onto same phone-identity account at first Google sign-in; never a duplicate account — for awareness, not for drawing)_
- **M01-03** (P0) — **OTP delivery is SMS-only and never silently degrades — the system uses no fallback mechanism (owner ruling 2026-08-06, Q47).** SMS is the delivery channel, and nothing is retried behind the user's back. The user gets a visible **resend** control, which unlocks at 30 s (M01-04, owner ruling 2026-08-06 Q44), and, if the code still does not arrive, a **"call me instead"** voice-OTP option — **retained as a USER-initiated option, not a system fallback**: the ruling names what "the system should not use", and a user whose SMS path is broken must still have a way in. If delivery fails, login fails loudly with a plain retry-later message — "No silent degradation on the front door," a principle this ruling **strengthens rather than weakens**, because nothing now happens invisibly at all. **When the SMS rail confirms a HARD delivery failure, that loud-failure state releases the resend cooldown immediately and offers the "call me instead" voice OTP in the same state (owner ruling 2026-08-06, Q51)** — the cooldown exists to stop resends while a message is still in flight, and once the network confirms failure nothing is in flight, so the user may act at once. What is released is the cooldown and nothing else: **`M01-04`'s anti-abuse caps are UNCHANGED and still bind** (3 requests per 15 min, 8 per day per phone, 5 failed verifies invalidate the OTP, 3 invalidations lock the number for 15 min) — where a cap is already reached the cap still governs and the honest message says so. *(This row previously read "**OTP delivery is layered and never silently degrades.** SMS is the primary channel, with automatic fallback to a secondary messaging-channel OTP where the market's OTP rail provides one, on delivery failure or a 30 s timeout. The user additionally gets a visible **resend** control and, if the code still does not arrive, a **“call me instead”** voice-OTP option. If every channel fails, login fails loudly with a plain retry-later message — “No silent degradation on the front door.”" — the automatic secondary-channel fallback clause is removed by this ruling; owner's words: "keep only resend feature after 30s that button get enabled, and the system should not use any fallback mechanism.")* *(This row previously stated nothing about the resend control inside that loud-failure state, and nothing about whether the voice OTP was offered there — the silence the Q47 closure pass recorded as M01 §6's open 0–30 s hard-failure question; owner ruling 2026-08-06 (Q51) supplies it and changes nothing else in this row.)* _(non-UI half, build-side: single-channel OTP delivery rail — SMS only, NO automatic fallback of any kind; the user-initiated voice-OTP option is retained; delivery failure surfaces loudly as retry-later — for awareness, not for drawing. This note previously read "layered OTP delivery rail: SMS primary, auto fallback channel on failure/30s, voice OTP option"; amended by owner ruling 2026-08-06, Q47)_
- **M01-04** (P0) — **OTP anti-abuse limits are product-visible.** Requests are capped (3 per 15 min and 8 per day per phone); resend has a cooldown; 5 failed verify attempts invalidate the OTP; 3 consecutive invalidations lock the phone number for 15 min with an honest message; invite sends are capped per tenant per day. **The resend cooldown is 30 seconds (owner ruling 2026-08-06, Q44)** — the value the journey already promises the user ("resend after 30 s", `S0.wrong.2`); docs/engineering/08's 45 s resend cooldown is **superseded**, and the UI resend control respects the ruled 30 s. Every other limit in this row is unchanged by the ruling. **`M01-03`'s delivery path is no longer layered (owner ruling 2026-08-06, Q47)** — its automatic secondary-channel fallback is removed, leaving SMS delivery plus this row's **resend** control and the user-initiated **“call me instead”** voice OTP; that sentence previously read “as is `M01-03`'s layered delivery path (SMS → fallback channel → voice OTP)”. **The cooldown is released immediately when the SMS rail confirms a HARD delivery failure (owner ruling 2026-08-06, Q51)** — the cooldown exists to stop resends while a message is still in flight, and once the network confirms failure nothing is in flight, so in `M01-03`'s loud-failure state the resend control is available at once and the user-initiated **“call me instead”** voice OTP is offered in that same state. **What is released is the cooldown alone: every cap in this row is UNCHANGED and still binds** — 3 requests per 15 min, 8 per day per phone, 5 failed verifies invalidate the OTP, 3 invalidations lock the number for 15 min — so where a cap is already reached the cap still governs and the honest message says so; the ruled 30 s continues to govern the ordinary in-flight case. *(This row previously read "**Recorded, not resolved:** the journey offers resend “after 30 s” (`S0.wrong.2`) while docs/engineering/08 sets a 45 s resend cooldown — the UI resend control must respect whichever cooldown is ruled; the divergence is carried in both source rows and recorded at `registers/conflicts.md` row 9." — that divergence, `registers/conflicts.md` row 9, is closed by this ruling.)* *(The cooldown's behaviour inside a confirmed hard-failure state was previously unstated in this row — the gap the Q47 closure pass recorded as M01 §6's open 0–30 s hard-failure question; owner ruling 2026-08-06 (Q51) supplies it and amends no limit here.)* _(non-UI half, build-side: rate limits: 3/15min and 8/day per phone, 30 s resend cooldown, 5-fail invalidate, 15-min lock, per-tenant invite cap — for awareness, not for drawing)_

## States

Base: **loading** · **empty** · **error** (empty/error states carry F7's teaching-empty-state contract — M01 §M01.1 behavior detail).

Screen-specific:

- **normal** — phone entry with Google Login offered alongside Mobile OTP (M01-02); no password field exists anywhere (M01 §M01.1 acceptance); no dead controls (MS12-17).
- **otp-entry** — 6-digit OTP entry after send.
- **otp-sent** — code dispatched on the SMS channel, which is the only delivery channel; nothing is retried behind the user's back (M01-03, owner ruling 2026-08-06 Q47). *(This state previously read "code dispatched on the primary SMS channel" — there is no secondary channel for it to be primary to.)*
- **otp-auto-read** — OTP entry auto-reads the code where the platform allows (M01 §M01.1 behavior detail).
- **wrong-code** — says what happened and what to do next (M01 §M01.1 behavior detail).
- **expired-code** — OTP failure state; says what happened and what to do next.
- **resend-cooldown** — visible resend control under its **30 s** cooldown (M01-04, owner ruling 2026-08-06 Q44). The countdown this state draws is 30 s; the earlier competing value is closed and recorded at `docs/prd/registers/conflicts.md` row 9. **This cooldown does not apply once a hard delivery failure is confirmed (M01-03, M01-04, owner ruling 2026-08-06 Q51)** — a confirmed hard failure releases it immediately, so this state does not render there; it governs only the ordinary case, where the message may still be in flight. *(Clause added by the Q51 closure pass: this state previously drew the 30 s countdown with no exception stated, the gap M01 §6 carried as the open 0–30 s hard-failure question.)*
- **call-me-instead** — voice-OTP option offered when the code still does not arrive; it is **user-initiated**, not a system fallback, and is retained on that basis (M01-03, owner ruling 2026-08-06 Q47). It is offered **immediately in the delivery-failed-retry-later state** as well, when the SMS rail confirms a hard failure (M01-03, owner ruling 2026-08-06 Q51). *(Clause added by the Q51 closure pass: this state previously named only the code-does-not-arrive trigger.)*
- **delivery-failed-retry-later** — loud failure: SMS delivery failed, it is said plainly, and the front door never pretends to be waiting (M01-03, M01 §M01.1 edge list). *(This state was named **all-channels-failed-retry-later** before owner ruling 2026-08-06 (Q47); there is one delivery channel now, so there are no "all channels" to fail.)* **On a confirmed hard delivery failure the resend control is available immediately in this state — no cooldown countdown, nothing to wait out — and the user-initiated "call me instead" voice OTP is offered here too (M01-03, M01-04, owner ruling 2026-08-06 Q51).** M01-04's anti-abuse caps are unchanged and still bind: if a cap is already reached at that moment, the cap governs and this state says so honestly (M01-04). **What the message SAYS in that confirmed-hard-failure case is not pinned by PRD — designer decides, and records the chosen wording back into this line** (`Q56`, reclassified 2026-08-06 as an implementation-time screen-copy item: no owner ruling is owed on it, none is pending, and nothing in the product waits on it). **The one constraint on the words is already fixed by `Q51`: the copy must not say "later" while the retry is live** — so `M01-03`'s *"retry-later"* wording is superseded in that case by `Q51` and cannot be the copy; the state's id is a label that follows the copy and never leads it, which is why it is not renamed here. Where the failure is **not** a confirmed hard one, nothing is superseded: `M01-03`'s plain retry-later message stands as written and the ordinary 30 s cooldown of **resend-cooldown** governs. *(Clause added by the Q51 closure pass: this state previously drew only the loud retry-later message and said nothing about the resend control or the voice option inside it.)* *(Opening clause and copy note added 2026-08-16 by the `Q56` pass: this state previously read "loud failure with a plain retry-later message" in the same line that makes the resend control available immediately — a contradiction to whoever draws it, and the brief carried no reference to `Q56` at all. See the dated amendment at the foot of this brief.)*
- **verified-success-dwell** — the confirmation beat after the code is accepted and before the post-auth handoff to the role-decided home. On a bad connection this is the only thing telling the user it actually worked, so the moment is drawn, not skipped. **The dwell duration is not pinned by PRD — designer decides, and records the choice here** (owner ruling 2026-08-07, `Q60`; same class as the `Q56` reclassification — this was never an owner preference, it is a value written when the screen is designed). Pick one duration, draw it, and write it into this line so the other platform inherits it rather than choosing a second answer; whatever is chosen applies to **both** platforms, which is what the `Q20` rebuild acceptance list means by "success-dwell timing". *(State added by the readiness pass, 2026-08-07: `Q20`'s acceptance list named success-dwell timing as binding, but no state carried it and no duration existed anywhere, so the moment would simply never have been drawn.)*
- **number-locked-15min** — 3 consecutive OTP invalidations lock the number for 15 min with an honest message (M01-04).
- **auth-error** — generic authentication failure, honestly stated.
- **google-link-first-sign-in** — the first Google sign-in runs the linking flow onto the same phone-identity account (M01-02).

*State removed by owner ruling 2026-08-06 (Q47), recorded not deleted:* **channel-fallback-fired** — which read "automatic fallback channel fired on delivery failure or the 30 s timeout (M01-03)". The system uses no fallback mechanism, so this state cannot occur and must not be drawn. The **resend-cooldown** state above was left untouched by Q47 and is the whole of the recovery path the system offers, alongside the user-initiated **call-me-instead**. *(That sentence previously read "The **resend-cooldown** state above is unchanged and is now the whole of the recovery path the system offers, alongside the user-initiated **call-me-instead**." — true of Q47, but no longer sayable as written: owner ruling 2026-08-06 (Q51) has since amended that state, releasing the cooldown immediately when a hard delivery failure is confirmed. Q47's own scope, the removed fallback, is untouched by Q51.)*

## Data volume

A single-record form: one phone number (normalized to the market's phone specification), one 6-digit OTP, and two delivery channels in play — SMS, plus the user-initiated voice OTP; no automatic fallback channel exists (owner ruling 2026-08-06, Q47 — this sentence previously read "up to three delivery channels in play (SMS → fallback messaging channel → voice)"). Design for all launch languages — signup and OTP screens exist in every launch language and default to the device locale (M01 §M01.1 localization notes).

## Numbers carrying provenance

Every rendered number carries its F8 provenance tier in the design. This screen's user-visible numbers are product policy constants, shown honestly per M01-04: the resend cooldown countdown (30 s — owner ruling 2026-08-06, Q44; the 45 s alternative is superseded), the request caps (3 per 15 min, 8 per day), the 5-failed-attempts invalidation, the 15-minute lock timer, and the 6-digit OTP length. No money, business quantity or business date renders here.
